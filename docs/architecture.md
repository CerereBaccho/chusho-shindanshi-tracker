# アーキテクチャ

本ファイルは設計判断の記録と全体構成の説明を目的とします。実装詳細ではなく「なぜこう設計したか」を残し、将来の判断材料とします。

## 全体構成

```text
index.html（単一ファイル）
├── <style>        CSS変数・レイアウト・コンポーネントスタイル
├── <body>         HTML構造（ホーム / 分析 / 設定 の3タブ）
└── <script>
    ├── PHASES[]   学習計画データ（定数）
    ├── TIPS[]     ランダム表示ヒント（定数）
    ├── store      localStorageラッパー
    ├── render()   ホーム画面の全DOM差し替え
    └── renderAnalysis()  分析タブのチャート・テーブル生成
```

外部依存なし。ブラウザで `index.html` を直接開けば動作する。

## コンポーネント

### PHASES 配列（定数）

- 責務: 11フェーズ分の学習計画を保持（科目名・期間・タスク・週末タスク・参考URLを含む）
- 入力: なし（ビルド時定数）
- 出力: `getPhase(dayIdx)` 経由で現在フェーズを返す
- 依存: なし

### store（localStorageラッパー）

- 責務: `localStorage` の get/set/remove/keys/clear を薄くラップし、呼び出し元をストレージ実装から切り離す
- キー設計: `day:YYYYMMDD`（日別データ）、`start-date`（開始日）、`notif-time`・`notif-enabled`（通知設定）
- 日別データ構造: `{ done: number[], minutes: number, manualTasks: ManualTask[] }`

### render()

- 責務: `viewDate`（閲覧中の日付）と `store` の状態をもとにホームタブ全体を再描画する
- 入力: グローバル変数 `viewDate`、`currentTab`
- 出力: DOM の直接書き換え
- 依存: `store`、`PHASES`、`computeTotals()`

### renderAnalysis()

- 責務: 科目別棒グラフ・週次サマリ・月次サマリのDOM生成
- 入力: `store` の全 `day:` キー
- 出力: DOM の直接書き換え
- 依存: `store`、`PHASES`

### 通知（Notification API）

- 責務: 毎日設定時刻にブラウザ通知を送る
- 実装: 30秒ポーリングで現在時刻と設定時刻を比較（ServiceWorkerなし）
- 制約: タブを開いている間のみ動作

### エクスポート（Blob / URL.createObjectURL）

- 責務: 学習記録を JSON / CSV ファイルとしてダウンロード
- 依存: ブラウザネイティブAPI

## データフロー

```text
ユーザー操作
    ↓
イベントハンドラ（toggleTask / logTime / addManualTask 等）
    ↓
store.set() → localStorage に書き込み
    ↓
render() 呼び出し
    ↓
store.get() → localStorage から読み出し
    ↓
DOM 差し替え（innerHTML / style）
```

## 設計判断（ADR風）

### 2026-04-22: 単一HTMLファイル構成を採用

- 背景: 個人学習ツールをできる限り手軽に使いたい。ビルドツール・ホスティングの管理コストを避けたい
- 選択肢: A. 単一HTML / B. Vite + React / C. Next.js
- 決定: A（単一HTML）
- 根拠: ブラウザで開くだけで動作し、依存管理が不要。学習データはlocalStorageに閉じているためサーバー不要
- トレードオフ: コードが1ファイルに集中するため規模拡大には向かない。現状のスコープ（個人利用）では問題なし

### 2026-04-22: フレームワークなし（Vanilla JS）を採用

- 背景: DOMの更新頻度が低く、状態管理の複雑さもない
- 選択肢: A. Vanilla JS / B. Vue / C. React
- 決定: A
- 根拠: `render()` の全画面差し替えで十分なパフォーマンスが出る。依存ゼロを維持できる
- トレードオフ: 機能追加時のコード分割が困難。スコープが固定されているため許容

### 2026-04-22: データ永続化に localStorage を採用

- 背景: バックエンドやDBを持たず、個人の1ブラウザで完結させたい
- 選択肢: A. localStorage / B. IndexedDB / C. 外部API
- 決定: A
- 根拠: 1日あたりのデータサイズは数百バイト以下。2年分（730日）でも5MB制限に収まる
- トレードオフ: ブラウザをまたいだ同期不可。データ消失リスクあり（エクスポート機能で対応）

## 問題データ管理（data/ フォルダ）

### 設計方針

PDF 問題集を直接ブラウザで解析する代わりに、手動で JSON に変換してから読み込む方式を採用する。

- 背景: ブラウザのセキュリティ制限により、ローカルファイルを直接読み込むには毎回ファイル選択が必要になる。あらかじめ JSON 化しておけばアプリとの連携が簡潔になる
- 原本 PDF は `data/pdf/` に保管し、変換済み JSON を `data/questions/` に配置する
- アプリは `data/questions/` の JSON を `fetch()` で読み込む（`python -m http.server` 経由）

### JSON スキーマ

`data/questions/schema.example.json` を正とする。主要フィールド:

| フィールド | 型 | 説明 |
| --- | --- | --- |
| `meta.subject` | string | 科目名（例: 企業経営理論） |
| `meta.source` | string | 出典（試験年度・種別） |
| `questions[].id` | string | 問題ID（例: R5-A-01） |
| `questions[].text` | string | 問題文 |
| `questions[].choices` | object | 選択肢 a〜d |
| `questions[].answer` | string | 正解記号（a/b/c/d） |
| `questions[].tags` | string[] | 分類タグ（省略可） |

### ファイル命名規則

`{試験種別}-{科目略称}-{年度}.json`（例: `1ji-keiei-2023.json`）

## アプリ内出題機能（設計）

外部リンク（CPAラーニング・過去問ドットコム等）へ遷移する代わりに、アプリ内で問題を出題し、その場で解答・採点・復習できる機能を設計する。本セクションは設計判断の記録であり、実装は段階的に行う。

### 解決したい課題

- 現状は各タスクに参考URLを貼り、ユーザーが自分で外部サイトへ遷移して演習している
- 外部遷移は「リンクを開く→該当箇所を探す→戻る」の摩擦が大きく、平日22:00-23:00の1時間に集中したい学習を妨げる
- 既に問題データの器（`data/questions/` のJSONスキーマ、PDF→JSON変換スクリプト）が用意済みで、これを画面に出すだけで摩擦を解消できる

### 設計の3軸と決定

| 軸 | 決定 | 主な根拠 |
| --- | --- | --- |
| データ格納 | HTML埋め込み ＋ ファイルインポート | `file://` のダブルクリック起動を維持しつつ、問題数増加に拡張可能 |
| 出題形式 | 4択MCQを主軸、簿記の穴埋めはフラッシュカード方式 | 既存スキーマに沿う。本番（1次）は4択中心 |
| 出題ロジック | Leitnerボックス（間隔反復）＋ 誤答優先キュー | 少コードで長期定着。「誤答は翌日再出題」方針と整合 |

### 2026-06-29: 問題データは「HTML埋め込み＋インポート」を採用

- 背景: 出題機能でも「ブラウザで開くだけで動作（依存ゼロ・単一ファイル）」という既存原則を維持したい
- 選択肢: A. HTML埋め込み / B. `fetch()` でJSON読込 / C. ファイルインポートのみ
- 決定: A（埋め込み）を基本とし、C（インポート）を併用
- 根拠: `fetch()` はダブルクリック起動（`file://`）だとCORS制約でローカルJSONを読めず、ローカルサーバー起動が必須になる。埋め込みは制約を受けない。問題数が肥大化した場合は、設定画面からJSONを取り込みローカル保存するインポート機能で補う
- トレードオフ: 大量問題を埋め込むと `index.html` が肥大化する。数百問規模までは許容し、それ以上はインポート方式へ寄せる

### 2026-06-29: 著作権のある過去問は「インポート方式のみ」で扱う（埋め込み禁止）

- 背景: 中小企業診断協会の過去問は個人利用に限り再配布・公開不可。`index.html` はコミット対象の本体であり、ここへ問題本文を埋め込むと著作物がリポジトリに混入する
- 決定: 著作権のある実問題データは**埋め込まず、ファイルインポート→`localStorage` 保存**のみで扱う。`index.html` 本体には問題を一切含めない
- 補足: 埋め込み（A）は著作権フリーの自作・サンプル問題に限定して使う。過去問JSON・PDFは `.gitignore` で除外済み
  - 除外対象: `data/pdf/`・`data/tmp_pages/`・`data/questions/*.json`（`schema.example.json`のみ許可）
- 実装: 設定タブの「問題データの読み込み」でJSONを取り込み、`qbank:{科目}-{年度}` キーで保存。`FileReader`経由のため`file://`でも動作する

### 2026-06-29: 出題ロジックに Leitnerボックスを採用

- 背景: 2年計画の長期学習で、一度解いた問題を忘れないよう再出題したい
- 選択肢: A. ランダム出題のみ / B. Leitnerボックス（5段階の間隔反復） / C. SM-2法（Anki相当）
- 決定: B（Leitnerボックス）
- 根拠: 各問に「ボックス段階」と「次回出題日」を持たせるだけで実装でき、SM-2より単純。正解で上の箱（出題間隔が延びる）、誤答で箱1（翌日再出題）へ戻す古典的手法で、長期記憶への定着効果は実証済み
- トレードオフ: SM-2ほど出題間隔の最適化は細かくない。個人利用のスコープでは十分

### 状態設計（localStorage）

問題ごとの学習状態を `localStorage` に保持する。既存のキー設計（`prefix:suffix`）に従う。

- キー: `srs:{questionId}`（例: `srs:R5-A-01`）
- 値: `box`・`due`・`correct`・`wrong`・`lastAnswered` を持つJSONオブジェクト
  - `box`: Leitnerの箱番号（1〜5）。数字が大きいほど出題間隔が長い
  - `due`: 次回出題日（`YYYYMMDD`）。この日以前の問題が出題対象
  - `correct` / `wrong`: 累計正答・誤答数（分析タブでの弱点把握に利用）
  - `lastAnswered`: 最終解答日（`YYYYMMDD`）

Leitnerの箱と再出題間隔の対応（初期案）:

| 箱 | 次回までの日数 |
| --- | --- |
| 1 | 翌日（1日） |
| 2 | 3日 |
| 3 | 7日 |
| 4 | 14日 |
| 5 | 30日 |

正解すると `box` を1つ上げ（最大5）、誤答すると `box` を1へ戻す。

### UI設計（初期案）

- タブに「演習」を追加（既存の ホーム / 分析 / 設定 と並列）
- 演習タブ: 科目フィルタ → 出題開始 → 1問ずつ表示 → 選択肢タップで即時正誤＋解説 → 次の問題
- ホームの「本日のタスク」に「今日の復習: N問」（`due` が当日以前の問題数）を自動挿入し、外部リンクを踏まずにその場で着手できるようにする
- 解答した演習時間を既存の学習時間へ自動加算（タスク完了時の時間自動加減算と同じ仕組み）

### 実装スコープ（段階）

1. 設計（本セクション）【完了】
2. MVP: 演習タブ＋4択ランダム出題＋即時正誤・解説＋JSONインポート（SRSなし）【完了 2026-06-29】
3. 間隔反復: Leitnerボックス＋誤答優先キュー＋ホームへの復習タスク差し込み【完了 2026-06-29】
4. 拡張: 簿記の穴埋めフラッシュカード、分析タブへの正答率表示【完了 2026-06-29】

段階2の実装メモ:

- 選択肢は5択（ア〜オ）に対応（`choices` は a〜e 可変キー、表示ラベルは `CHOICE_LABEL` でア〜オに変換）
- 問題バンクは `qbank:{科目}-{年度}` キーで `localStorage` に保存。`getBanks()` で列挙
- `explanation` が空の問題は解説欄を表示しない（公式は解説非公開のため）
- 初回データ: 経営情報システム 令和5年度25問を `data/questions/1ji-joho-2023.json` に作成済み（gitignore対象）

段階3の実装メモ:

- SRS状態は `srs:{questionId}` に `{box, due, correct, wrong, lastAnswered}` で保存
- 箱と間隔: `SRS_INTERVALS={1:1,2:3,3:7,4:14,5:30}`。正解で `box+1`（最大5）、誤答で `box=1`。次回期限は本日＋間隔日
- 演習に「復習」モードを追加。`due <= 本日` の問題のみを箱昇順（誤答優先）で出題
- ホームは `countDueReviews()` で期限到来数を数え、`#review-section` に「今日の復習: N問」＋復習ボタンを差し込む（`startReview()`）
- 未解答の問題は `srs` レコードを持たず復習対象外（=新規は通常出題で学習し、解答後に復習サイクルへ入る）

段階4の実装メモ:

- `choices` が無い問題はフラッシュカードとして描画（簿記の穴埋め・分類・表作成など）。「答えを表示」→解答表示→自己採点「できた／できなかった」で`updateSrs`を呼ぶ
- 解答描画は `renderFlashcardAnswer()`。`answer.description` と `answer.items` を整形（`{no,value}`・`{category,items}`・文字列に対応、未知形状は`JSON.stringify`）
- 選択問題・フラッシュカード共通の採点後UI（正誤＋次へ）を `finishAnswer()` に集約
- 分析タブに「演習の成績」表を追加（`renderQuizStats()`）。SRSの累計`correct`/`wrong`から科目別に、学習済／累計正答率／復習待ちを集計

## 非機能要件

- **パフォーマンス**: `render()` の全画面再描画を1秒未満で完了（データ量が少量のため問題なし）
- **オフライン対応**: 完全オフライン動作（ネットワーク依存なし）
- **プライバシー**: 学習データは端末のlocalStorageにのみ保存。外部送信なし
